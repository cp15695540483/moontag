# `tools/samples/` 压缩帧夹具说明

本目录下 6 个 `*.mp3` 是 **ID3v2.3 / v2.4 帧级压缩（frame compression）** 的测试夹具，
由仓库内脚本生成，用于覆盖「压缩帧不得阻断整个标签读取」这条行为。

## 1. 生成方式与来源

| 项目 | 内容 |
|---|---|
| 生成器 | [`tools/make_cframe_fixtures.py`](../make_cframe_fixtures.py)（纯 Python，零 `moon` 调用、零网络、不依赖 moontag） |
| 命令 | `python tools/make_cframe_fixtures.py`（生成 + 回读自检）；`python tools/make_cframe_fixtures.py --verify`（只读校验：独立解析 + 磁盘字节 == 重新构造的字节） |
| 音频来源 | `tools/samples/v24.mp3`（ID3v2.4 基准）与 `tools/samples/v23.mp3`（ID3v2.3 基准），两者均由 [`tools/make_samples.sh`](../make_samples.sh) 用 ffmpeg 的 `sine` 信号源生成 |
| 改动范围 | **只替换文件开头的 ID3v2 标签区**；标签之后的音频体逐字节取自上述基准文件（各 8567 字节），脚本内逐字节断言 |
| 确定性 | 脚本不写时间戳 / 随机数 / 主机路径；同一输入连跑两次产出逐字节一致（见 §5）。重新生成需同一 Python/zlib 版本才能得到同样的 sha256 |
| padding | 本组夹具**不含**标签尾部 padding；标签头尺寸字段 = 帧区总长度（基准样本自带 10 字节 padding，本组没有） |

6 个夹具里 **只有标签区**不同，音频体完全一致（均 = 基准 `v24.mp3` / `v23.mp3` 的 8567 字节音频）。

## 2. 规范依据

- **ID3v2.3.0 §3.3.1**：帧头 = `ID(4)` + **普通大端 u32** 尺寸(4) + 状态标志(1) + 格式标志(1)；
  格式标志 `%ijk00000`，`i=$80` = 压缩；置了压缩位时，帧头之后追加 **4 字节普通大端 u32** = `decompressed size`；
  压缩算法点名 zlib（RFC 1950）。
- **ID3v2.4.0 §4.1.2**：帧头 = `ID(4)` + **synchsafe u32** 尺寸(4) + 状态标志(1) + 格式标志(1)；
  格式标志 `%0h00kmnp`，`k=$08` = 压缩、`p=$01` = 数据长度指示（DLI）；
  压缩时 **必须**同时置 DLI（→ `$09`）；DLI 是 **4 字节 synchsafe u32**，
  语义＝「所有 format flags 归零时应写的 Frame length」，即**解压后**的载荷长度。
- **附加头顺序**（本组夹具不加密、不分组，因此不出现加密方法/组号字节）：
  `v2.3 = [尺寸指示 4B][加密方法 1B][组号 1B]`，`v2.4 = [组号 1B][加密方法 1B][DLI 4B]`。
- **版本差异的准确边界**：标签头的 10 字节尺寸字段在 v2.3 与 v2.4 中**都是 synchsafe**；
  只有**帧**的尺寸字段不同（v2.4 synchsafe / v2.3 普通大端 u32）；长度指示字段同理不同
  （v2.4 DLI synchsafe / v2.3 decompressed size 普通大端 u32）。
  synchsafe 的每个字节只允许低 7 位，**最高位为 1 即为非法编码**。
- 所有文本帧载荷 = 编码字节 `0x03`（UTF-8）+ UTF-8 文本。

### 合法性声明（重要）

**帧级压缩不是主流标签工具会写出的产物**——这些夹具不是某个工具导出的现成文件，
而是按 id3.org 的 id3v2.3.0 §3.3.1 与 id3v2.4.0-structure §4.1.2 **手工构造**的合法标签：
帧头标志位、长度指示、zlib 流、标签头尺寸字段都逐条对照规范书写，并由脚本内的独立解析器
（不经过 moontag 代码）逐帧回读验证。它们代表「规范允许但少见」的输入，因此专门用来固定
库对这类输入的行为。

第三方交叉验证：本组夹具**未做**第三方解析器交叉验证（生成环境不联网、未安装 mutagen）。
既有探针报告 `_tmp_cframe_probe/REPORT.md` §3 记录过 ffmpeg 7.1 能读出 v2.4 压缩帧文本、
对 v2.3 压缩帧静默丢帧——本次**未复跑**该实验，仅作参考。

对照组 `control_v24.mp3` / `control_v23.mp3` 与对应压缩夹具**同文本、同帧顺序**，
唯一差别是格式标志为 `0x00` 且不写长度指示、不压缩载荷：因此两者读数差异只能归因于压缩标志。

文本串（脚本里的常量，`REPEAT = "0123456789" × 5000`）：

- `ARTIST = "CompressedArtist-" + REPEAT` → 50017 字符，UTF-8 载荷 **50018 字节**
- `TITLE = "CompressedTitle-" + REPEAT` → 50016 字符，UTF-8 载荷 **50017 字节**
- `TXXX_VALUE = "irrelevant-value-" + REPEAT` → 50017 字符；TXXX 载荷 = `0x03` + `"probe"` + `0x00` + 值 = **50024 字节**

> 为什么重复 5000 次：`0123456789` 这种周期串的 deflate 压缩比极高（约 130:1），
> 只有把重复次数拉到这个量级，zlib 流才会 > 127 字节（实测 152 字节），
> 压缩帧的帧尺寸字段才能 ≥ 128 —— 也只有 ≥ 128 时，synchsafe 与普通大端 u32 写出的字节才**不同**。
> 实测：重复 4000 次 → 131 字节，5000 次 → 152 字节（取 5000 留出跨 zlib 版本的余量）。

## 4. 逐帧字节级清单

字体：`尺寸字段` 指帧头第 5–8 字节的原始字节；`状态` = 帧头第 9 字节；`格式` = 帧头第 10 字节。
音频起点 = 标签头 10 字节 + 标签头尺寸字段值（文件总长 = 音频起点 + 8567）。

## 5. 脚本自检与幂等性

脚本内独立解析器逐帧断言以下内容，任一不成立即非零退出（退出码 1）：

1. **(a) 尺寸编码方式**：v2.4 帧尺寸按 synchsafe 解码、v2.3 按普通大端解码，必须等于磁盘载荷长度；
   v2.4 还要满足**规范形式** `synchsafe(尺寸) == 原始字节`（只「解码后数值相等」不算通过）；
   标签头尺寸字段必须能按 synchsafe 无损重编码回原字节。
2. **(a2) 压缩流长度**：每个压缩帧的 zlib 流必须 **> 127 字节**、帧尺寸字段必须 **≥ 128**，
   以保证 synchsafe 与普通大端 u32 在这些字节上确实不同。
3. **(b) 长度指示一致**：`DLI`（v2.4，synchsafe，且必须是规范形式）/ `decompressed size`（v2.3，大端）
   == `len(zlib.decompress(压缩部分))` == 期望载荷长度。
4. **(c) 解压文本**：解压结果逐字节等于期望载荷（含编码字节 `0x03` 与完整文本）。
5. **(d) 音频体**：标签之后的字节与基准 `v24.mp3` / `v23.mp3` 的音频体逐字节一致。

诊断行对「误读」只打印**真实计算结果**：synchsafe 误读时逐字节检查最高位，非法就写
「synchsafe 误读非法（第 N 字节最高位为 1）」，并另给按低 7 位强行解码的值。

幂等性证据（本次会话连跑三次，逐文件 sha256 对比，6/6 `IDENTICAL`）：

```

control_v23.mp3        run2=1A2CB083A917670E run3=1A2CB083A917670E IDENTICAL
cframe_v24.mp3         run2=C604AF8086A1F949 run3=C604AF8086A1F949 IDENTICAL
cframe_v24_tit2.mp3    run2=4BB2814E9810B977 run3=4BB2814E9810B977 IDENTICAL
cframe_v24_txxx.mp3    run2=D00DB7B525651A9D run3=D00DB7B525651A9D IDENTICAL
cframe_v23.mp3         run2=E008FC86CF853DEA run3=E008FC86CF853DEA IDENTICAL
```

反例测试（在内存里逐字节篡改后调 `verify`，12 例全部被检出、退出非零），覆盖：
v2.4 帧尺寸字段改写成大端字节、v2.4 DLI 改写成大端字节、DLI 数值 +1、zlib 流字节翻转、
压缩标志清 0、只置压缩不置 DLI、音频体字节翻转、v2.3 尺寸字段/DLI 互换编码方式，等等。

## 6. 与早期规格的差异（已按 Lead 要求收紧）

1. **「压缩流 > 127 字节」现已满足**：zlib 流实测 152 / 153 / 156 字节
   （分别对应 `cframe_v24.mp3` 的 TPE1、`cframe_v24_tit2.mp3` 的 TIT2、`cframe_v24_txxx.mp3` 的 TXXX；
   `cframe_v23.mp3` 的 TPE1 为 152），对应帧尺寸字段 156 / 157 / 160 / 156，均 ≥ 128。
   代价是占位文本从最初的「重复 20 次」提到「重复 5000 次」：`0123456789` 周期串的 deflate
   压缩比约 130:1，重复次数少时压缩流根本涨不到 128 字节（20 次 → 38 字节，4000 次 → 131 字节）。
   因此两个**对照组**变成 58626 字节（含一个 50018 字节的未压缩长帧）。
   前缀文本 `CompressedArtist-` / `CompressedTitle-` / `PlainTitle` / `PlainArtist` **未改动**。
2. **诊断行已修正**：早期版本打印「若误读为 synchsafe 则得 218」，这是错的——
   `00 00 00 DA` 的第 4 字节 `DA` 最高位为 1，按 synchsafe 读属于**非法**，
   不存在「得 218」这回事。现在改为逐字节判定并如实描述（见 §5 末尾）。
3. 原始任务描述里「`CompressedArtist-` + `0123456789`×20 = 共 520 字符」的算式有误，
   该拼接实际是 217 字符；本组夹具以 `REPS = 5000` 为准（Lead 已明确要求压缩流 > 127 字节）。
4. 未做第三方解析器交叉验证（见 §2 合法性声明末尾）。
